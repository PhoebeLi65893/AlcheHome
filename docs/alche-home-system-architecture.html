1. Architecture Overview & Principles

This document translates the Alche Home PRD/TRD into a buildable architecture. The system is a message-first, event-driven platform: homeowners and handymen interact mainly through SMS/WhatsApp and a lightweight web app, while a Gemini-powered agent performs triage and ticket creation, and a matching service dispatches jobs.

Guiding principles
  • Channel-agnostic core: web chat, SMS and WhatsApp all normalize into one internal message format.
  • Stateless services, stateful stores: conversation state lives in PostgreSQL/Redis so Cloud Run instances can scale to zero.
  • Asynchronous by default: webhooks are acknowledged immediately and processed via a queue.
  • Privacy by design: number masking, PII redaction before any data reaches the Knowledge Base.
  • Modular monolith first: one deployable API with clear module boundaries; the Fine-Tuning pipeline is separate.

3. Low-Level Components (C4 Level 3)

3.1 Core API Modules

  • auth: OIDC callbacks (Google, Facebook), email/password, magic links, JWT issue/refresh, guest-account linking by phone number.
  • channels: adapters (WebAdapter, TwilioSmsAdapter, WhatsAppAdapter) converting to a unified InboundMessage {userId, channel, text, mediaRefs, ts}.
  • conversations: persists every turn, assigns it to a session, publishes message.received events.
  • tickets: ticket lifecycle and state machine (section 3.3).
  • handymen: profiles, skills, service zips, availability, rating.
  • bridge: creates and closes proxy sessions between customer and handyman.

3.2 AI Agent Service Internals

  1. Context Builder: loads last N turns, ticket draft, and RAG snippets from pgvector.
  2. Media Preprocessor: fetches signed GCS URLs, resizes images, passes them to Gemini as multimodal parts.
  3. Gemini Client: Flash for routine turns, Pro for image-heavy or ambiguous diagnosis; retries with exponential backoff.
  4. Tool Router: executes create_repair_ticket and read-only lookups, validating arguments against the schema.
  5. Safety Layer: detects emergencies (gas smell, active electrical fire) and returns "call 911" guidance instead of dispatching.

3.3 Ticket State Machine

DRAFT --(create_repair_ticket)--> OPEN --(matching starts)--> MATCHING
MATCHING --(handyman ACCEPT)--> ASSIGNED --(bridge active)--> IN_PROGRESS --> COMPLETED --> RATED
MATCHING --(all decline / timeout)--> UNMATCHED --(retry / escalate to ops)--> MATCHING
ANY --(user cancels)--> CANCELLED

3.4 Matching Algorithm

  1. Filter: category skill, service zip, currently available, not blocked.
  2. Score: 0.4*proximity + 0.3*rating + 0.2*response_rate + 0.1*urgency_fit.
  3. Offer to top-ranked handyman; wait for urgency-based timeout (EMERGENCY 3 min, SAME_DAY 15 min, FLEXIBLE 2 h).
  4. On decline or timeout, move to next; after 5 attempts mark UNMATCHED.

Idempotency: every webhook stores its provider message ID with a unique constraint; replays return 200 without reprocessing. Failed jobs go to a dead-letter queue with alerting.

7. Security, Reliability & Observability

7.1 Security Controls

  • Identity: OIDC with minimal scopes (email, profile); short-lived JWTs (15 min) and rotating refresh tokens; RBAC by role.
  • Privacy: masked proxy numbers; handyman receives only first name, zip and issue until acceptance; address shared only after ASSIGNED.
  • Data protection: AES-256 at rest (CMEK optional), TLS 1.3 in transit; field-level encryption for phone numbers.
  • PII redaction: Cloud DLP plus regex rules before any record enters kb_chunks or tuning datasets; opt-out flag honored.
  • Abuse controls: per-user rate limits, upload size and MIME validation, malware scan on media, prompt-injection guardrails (tool arguments validated server-side).

7.3 Observability

  • Structured logs with ticket_id and conversation_id correlation; OpenTelemetry traces across API, queue and agent.
  • Dashboards: match rate, time-to-accept, Gemini latency/error rate, token spend, SMS delivery rate.
  • Alerts: DLQ depth, webhook failures, UNMATCHED tickets older than 15 minutes, LLM quota exhaustion.

Delivery Roadmap

  1. Phase 1 (MVP): auth, web chat, Gemini intake, ticket creation, SMS dispatch with manual ops fallback.
